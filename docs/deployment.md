# Render + Vercel Deployment

## Important: MySQL is external

Render Blueprints can provision Render Postgres, not MySQL. This project intentionally remains on MySQL, so create a reachable MySQL 8.0+ database with your chosen provider. Check that provider's current price, free-tier limits, TLS instructions and network allow-list before creating it. Render's free web service can sleep when idle; the first request after sleep may be delayed.

Do not point this app at the local Docker volume. A deployed Render service needs a persistent, externally reachable database. Use TLS and the narrowest provider network allow-list available.

## Prerequisites

- Push this project to a GitHub repository you control. This workspace does not currently have a connected Git remote.
- Create the external MySQL database and keep its host, port, database, username, password and (if required) CA certificate available for the Render Dashboard. Do not commit these values or paste them into source files.
- A Render account and a Vercel account connected to the repository.

## Deploy the API to Render

1. In Render, choose **New > Blueprint**, select the connected repository, and let Render read the root `render.yaml`.
2. Supply the prompted `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_SSL_CA` (if the provider requires a custom CA), and `CORS_ORIGIN` values. Set `CORS_ORIGIN` after Vercel gives you the production site URL, for example `https://your-pool.vercel.app`.
3. `JWT_SECRET` is generated by the Blueprint. Keep `SEED_DEMO_DATA=false` on a public deployment so the shared demo passwords are not seeded into production.
4. Deploy and wait for the `/health` check to pass. Record the API origin, for example `https://dhaka-tesla-pool-api.onrender.com`.

The API binds to Render's injected `PORT` and listens on `0.0.0.0`. The Docker/Compose setup continues to use port 4000 locally. Startup applies the schema migration before serving requests.

## Deploy the frontend to Vercel

1. Import the same GitHub repository into Vercel. Keep the project root at the repository root; Vercel detects Vite and builds `dist` with `npm run build`.
2. Add `VITE_API_URL` in the Vercel project environment settings for Production (and Preview if needed). Set it to the Render API origin only, with no trailing slash or `/api`; for example `https://dhaka-tesla-pool-api.onrender.com`.
3. Deploy. The `vercel.json` rewrite supports the Vite single-page app, and the client sends requests to `${VITE_API_URL}/api/...`.
4. Copy the final Vercel production URL into Render's `CORS_ORIGIN`, then redeploy the API if required.
5. Open `/health` on the Render origin and sign up a driver or passenger on the Vercel URL.

The `VITE_API_URL` value is embedded in the frontend at build time. If it changes, trigger a new Vercel deployment. Vercel preview domains need their own allowed `CORS_ORIGIN`; this app currently accepts one exact origin per Render service.

## Database TLS

The Render Blueprint enables `DB_SSL=true` and certificate verification. If the MySQL provider uses a public CA trusted by Node, `DB_SSL_CA` can be blank. If it provides a custom CA, put that PEM certificate in the Render `DB_SSL_CA` environment variable. Locally, Compose defaults TLS off for the local MySQL container; `DB_SSL`, `DB_SSL_REJECT_UNAUTHORIZED` and `DB_SSL_CA` can be set in `.env` for an external DB.

## Limits and cost

Render and Vercel service plans and quotas can change. The API Blueprint uses Render's `free` compute plan, which may spin down while idle; Vercel hosts the static frontend. Neither platform entry creates the required MySQL database. Confirm the MySQL provider's current terms before deployment; do not assume a free MySQL tier is available.
